> 前一版：[`roadmap-2.1.md`](roadmap-2.1.md)

## 零、这一版为什么不铺适配器

2.1 加了三个适配器，谱系确实好看了。但**再加两个适配器，项目不会因此更值钱**。

现在 MetaPool 已经能证明的三件事：

1. 能把五类异构资源纳入一套治理（生命周期 / 指标 / 调参 / 停机）
2. 能力接口设计经得起真实实现的检验（两个新接口零 `UnsupportedOperationException`）
3. 扩展点是真的（三次加 adapter，核心零改动，可核验）

**这三件事，加第六个适配器一件也不会加强。** 所以 2.2 的重点是补短板，
排序依据是「不做会怎样」，不是「好不好做」。

## P0-A：`metapool-core` 故障路径补测 ✅ 已完成（2026-08-12）

**动机**：core 是**唯一被所有资源共用的代码**，出问题时五类资源同时受影响，
且最难在使用方现场复现。而它此前只有 6 条测试，五个适配器加起来却有 90+ 条 ——
覆盖最薄的恰恰是最该厚的地方。原有测试覆盖的都是顺利路径（注册、启停顺序、聚合健康、调参路由）。

**做了什么**：新增 `ControlPlaneFailurePathTest`（16 条），只测「有人抛异常时会发生什么」。
贯穿全文件的判据一句话：**治理面必须比被治理者更结实。**

覆盖：

| 面 | 用例 |
|---|---|
| 停机容错 | 某资源 stop 抛异常，其余仍逆序停完；全部失败时 close 仍不抛；重复 close |
| 启动回滚（P-11） | **回滚过程中再抛异常，不得掩盖首因**（挂 suppressed）；首个资源就失败时无可回滚 |
| 聚合健康 | 某资源 health() 抛异常不击穿聚合（**发现真缺陷，见下**）；DOWN 压过 DEGRADED；空控制面为 UP |
| 指标绑定 | 维持快速失败，并把这个取舍钉住 |
| 注册表 | 同名并发注册只成功一次；异名并发一个不丢；只读快照；未知名查找/调参 |
| 语义钉子 | 启动后再注册不会被自动启动；close 后 start 会重启 |

### 🔴 发现并修掉一个真缺陷 → 台账 P-23

`DefaultResourceManager.health()` 直接传播资源抛出的异常，于是**一个行为不端的适配器
能让整个 `/actuator/health` 报错**——聚合健康恰恰是出事时要看的东西，最需要它的时刻正好不可用，
而且运维看到的是一个与真实故障无关的异常，排查方向从一开始就被带偏。

契约确实要求 `health()` 不抛异常，但**契约管不住第三方 adapter**，而 2.1 之后 SPI 扩展是
明确鼓励的（`metapool.resources.<type>` 就是为它开的口子）。

修法：逐资源 try/catch，抛异常或返回 `null` 的计为 **DOWN 并在 detail 里点名**，其余照常聚合。
已验证修复前该用例确实失败。

**一条刻意的不对称**（同轮想清楚并写成测试钉住）：

| 方法 | 策略 | 理由 |
|---|---|---|
| `close()` | 容错，逐个继续 | 停机常发生在没人盯着的时刻，半途而废会让后面的资源泄漏到 JVM 结束 |
| `health()` | 容错，计为 DOWN | 出事时才看它，不能被一个坏适配器整个搞挂 |
| `bindMetrics()` | **快速失败** | 绑不上是接线错误、发生在启动期，**大声失败好过静默少一半指标**——后者会让人在故障时对着缺曲线的看板做判断 |

判据是「这个失败发生在什么时候、瞒着人会怎样」，**不是「统一都 try-catch 显得整齐」**。

## P0-B：examples 加故障演示端点 ✅ 已完成（2026-08-12）

**动机**：examples 是面试时最可能被点开的东西。它现在能展示「能跑」，
但展示不了 MetaPool 最有说服力的场景 —— **出问题的时候治理面怎么帮你**。

**做了什么**：`SaturationController`，三个端点 —— `POST /demo/saturate/{name}?seconds=N`、
`POST /demo/release/{name}`、`GET /demo/saturation`。

**它按能力接口分派，不按类型字符串**：怎么打饱和取决于资源**有什么能力**
（`ManagedExecutor` 塞满 / `Pool<T>` 借光 / `RateLimiter` 抽干），而不是它**是什么类型**。
这段分派本身就是能力隔离的演示 —— 新增资源类型时它不需要认识你，只要实现了某个已知能力即可。

**两处不显然的地方**：

1. **池类资源光借光还不够，必须再制造一个排队者。** `HikariAdapter.health()` 的降级判据是
   「无空闲 **且** 有人在等」——「借满」本身不是故障，那正是池在满负荷工作。
   要演示降级就必须真有人排队，否则演示会静悄悄地什么都不发生。
2. **限流器被抽干不会降级**，响应里为此专门带一句说明：拒绝流量正是它在履职，
   该看的是指标（可用令牌归零、拒绝计数上涨）而不是健康状态。
   宁可在响应里解释清楚，也不为了「演示效果」把它硬报成 DEGRADED。

**验收**：`saturateEndpoint_degradesHealth_andReleaseRestoresIt` 断言三段状态
（UP → DEGRADED（且聚合健康点名）→ 释放后 UP）。测的不是「能打饱和」，
而是**治理面看得见** —— health 不跟着变，这个端点就只是个玩具。

## 2.3.0：`adapter-lettuce` ✅ 已完成（2026-08-13）

**这个适配器的价值不在实现，在于先回答一个问题**：

> Lettuce 是**单连接多路复用**，一个 `StatefulRedisConnection` 天然线程安全、可被所有线程共享，
> **根本不需要池化**。那它到底该不该实现 `Pool<T>`？

| 方案 | 说明 | 风险 |
|---|---|---|
| **A. 只做治理，不实现 `Pool`**（✅ 已拍板并实现） | 纳管连接生命周期 + 健康 + 指标 | 最诚实；但「redis adapter 不是池」可能让人意外，需在文档正面解释 |
| B. 实现 `Pool<StatefulRedisConnection>` | 用 Lettuce 的 `ConnectionPoolSupport`（内部就是 Commons Pool2） | 只在阻塞命令 / 事务 / pipeline 独占场景才需要池；平时池化反而是反模式 |
| C. 两者都给 | 默认 A，配置开启才走 B | 复杂度上升 |

**结果：拍板 A，已实现。** 完整论证见 [`adapter-lettuce.md`](adapter-lettuce.md)，
其中最值得记住的一点是——**这次的错误会比 1.0 那次更隐蔽**：

| | 1.0 的错（P-07） | 这次可能犯的错 |
|---|---|---|
| 表现 | `acquire()` 抛 `UnsupportedOperationException` | `borrow()` 正常返回，`release()` 正常返回 |
| 会被发现吗 | 会，一跑就炸 | **不会**，测试全绿、功能正常 |
| 危害 | 立刻暴露 | 契约在撒谎，直到有人真按池语义用它（如在"借来"的连接上跑事务） |

23 条测试（16 本地 + 7 真 Redis），核心零改动。其中 `connection_isSharedNotPooled`
断言两次 `connection()` 返回 `assertSame` —— **这就是「没有借还语义」的实证**。

判据一句话：**不能因为「别的 adapter 都实现了 `Pool`」就让它也实现——那是用一致性绑架语义。**
`Bucket4jAdapter`（限流不是池）、`RedissonLockAdapter`（锁不是池）是同一个判断的前两次，
只不过那两次更明显。

**它反而实现了 `Tunable`**（`command-timeout` 运行时真可写），而 Redisson 适配器不实现——
同一条判据（有没有真参数），两个相反结论。这正是可选能力接口在正常工作的样子。

## 发布节奏

**P0-A + P0-B 做完即可发 2.2.0**，lettuce 单独作为 2.3.0 —— 它带一份独立的设计文档，
本身就是一个完整的叙事单元。

小步发版对作品集更有利：Central 上有多个版本的演进轨迹，比一个大版本更能说明「在持续维护」。

## 执行纪律（沿用）

- 代码前先确认设计；接口/边界决策先出方案拍板（RULES §1.1）
- 核心零改动是**新 adapter** 的验收线（§2.8）；core 自身的改动不在此列，但要有测试先行
- 每踩一个坑当场追加台账（现已到 **P-23**）
- 报测试结果**同时报通过数与跳过数**（§4.3）
- 新增 adapter 后同步：examples / Grafana 看板 / **告警规则** / README 两版 / CHANGELOG / PUBLISHING 构件表
